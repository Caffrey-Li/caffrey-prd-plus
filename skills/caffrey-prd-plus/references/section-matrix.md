# 文档版本与章节取舍

PRD 有三个版本，用户在第 1 步选择版本，再按板块增减。版本和板块决定写哪些章节、每章写多细；章节编号在任何版本中都不变。

## 一、三个版本

| 版本 | 写什么 | 适合 |
| --- | --- | --- |
| 精简版 | 背景两三句、目标、改动点（线框图 + 字段 + 规则）、验收、风险 | 改字段、调文案、加一个筛选、改一条规则参数；单一模块，不跨部门，无数据结构变更 |
| 核心版 | 精简版 + 场景、方案、范围、流程、状态、权限等研发测试必需的内容；协作、规范、数据、上线等可按板块加选 | 有新页面或新流程；涉及 2-3 个模块或 1-2 个协作部门；有少量数据结构变更 |
| 完整版 | 全部 16 章 + 附录 | 新产品或新业务线；跨多个系统或部门；有架构调整或数据迁移；B 端交付项目；硬件项目；需要给管理层、客户或法务评审 |

## 二、推荐哪个版本

1. 按上表判断，满足某一档的任一条就推荐那一档；同时满足多档时取较高的一档。
2. **默认推荐精简版**；拿不准时也推荐精简版，用户需要时再加板块或升级版本。
3. 在第 1 步确认中写出推荐版本和一句理由，并列出另外两个选项。
4. 用户可以在版本基础上加减板块，例如“核心版，加上数据与埋点”“完整版，不要里程碑”。照做，并在信息卡「文档版本」写成“核心版 + 数据与埋点”。

## 三、板块与章节

第 1 步让用户勾选的是板块，一个板块对应一个或几个章节。「零、文档信息」任何时候都有，不作为板块。

| 板块 | 对应章节 | 精简版 | 核心版 | 完整版 |
| --- | --- | --- | --- | --- |
| 背景与目标 | 一、三 | ✓ | ✓ | ✓ |
| 用户与场景 | 二 | | ✓ | ✓ |
| 方案与范围 | 四、五 | | ✓ | ✓ |
| 功能与规则 | 8.1 功能清单、8.2 流程、8.5 状态、8.6 权限、8.7 规则、8.8 对接 | ✓（只写 8.1 和改动涉及的规则） | ✓ | ✓ |
| 页面线框图 | 8.3 用户路径、8.4 页面说明与线框图 | ✓ | ✓ | ✓ |
| 字段与组件 | 8.4 字段表、8.9 字段字典 | ✓ | ✓ | ✓ |
| 全局与交互规范 | 七 | | | ✓ |
| 协作与影响 | 六 | | | ✓ |
| 类型与行业要点 | 九 | | | ✓ |
| 非功能需求 | 十 | | | ✓ |
| 数据与埋点 | 十一 | | | ✓ |
| 验收标准 | 十二 | ✓ | ✓ | ✓ |
| 上线计划 | 十三 | | | ✓ |
| 风险与待决 | 十四 | ✓ | ✓ | ✓ |
| 里程碑 | 十五 | | | ✓ |

- 用户取消了「页面线框图」时，8.4 只写文字说明；取消「字段与组件」时，不写字段表和 8.9。
- 行业合规项（见第五节）不受板块限制，没选「类型与行业要点」时写进相关章节或第十四章。

下表是各章在不同版本中写多细；用户增减板块后，以用户的选择为准。

### 各章在不同版本中的写法

图例：● 必须写　◐ 按条件判断（见第四节）　○ 可选　— 不出现（直接省略，不写不适用）

| 章节 | 精简版 | 核心版 | 完整版 |
| --- | --- | --- | --- |
| 零、文档信息 | ●（信息卡只保留需求名称、文档版本、优先级、文档状态、当前版本、产品负责人；摘要 1-2 句；不写目录） | ●（不写目录） | ● |
| 一、背景与问题 | ●（2-3 句） | ●（问题、来源、为什么现在做） | ● |
| 二、用户与场景 | — | ◐（只写核心场景表） | ◐ |
| 三、目标与成功标准 | ●（1 个指标，或“无量化目标 + 原因”） | ●（指标表；非目标、验证方式可选） | ● |
| 四、方案概述 | — | ●（一段话方案 + 主流程概要） | ● |
| 五、范围与版本规划 | — | ●（本期做 / 不做；版本规划可选） | ● |
| 六、协作与影响范围 | — | —（加选时只写 6.2、6.6） | ●（六张表全写） |
| 七、全局与交互规范 | — | —（加选时只写本需求用到的条目） | ● |
| 八、需求详情 | ●（8.1 + 改动页面的线框图、字段与组件、规则） | ●（8.3 用缩进列表） | ●（8.3 每个模块一张用户路径图） |
| 九、类型扩展模块 | — | —（加选时只保留相关的检查项） | ● |
| 十、非功能需求 | — | —（加选时写） | ● |
| 十一、数据与埋点 | — | —（加选时只写 11.1） | ● |
| 十二、验收标准与测试要点 | ● | ● | ● |
| 十三、上线与运营计划 | — | —（加选时写几行） | ● |
| 十四、风险、依赖与待决问题 | ●（1-3 条，待确认问题直接列在这里） | ● | ● |
| 十五、里程碑与效果追踪 | — | — | ● |
| 附录 | ◐（只保留变更记录，定稿后才出现） | ◐（名词解释、变更记录、确认记录按需） | ● |

精简版、核心版保留原章节编号（例如“零、一、三、八、十二、十四”），不重新编号。

## 四、条件章节的判断规则

| 章节 | 写 | 写【不适用】（完整版）或省略（精简版、核心版） |
| --- | --- | --- |
| 二、用户与场景 | 有用户或客户直接感知的变化 | 纯技术改造、纯数据底层建设 |
| 六、协作与影响范围 | 涉及其他系统、部门或外部依赖 | 单一系统内、本团队可独立完成 |
| 七、全局与交互规范 | 有界面 | 无界面时 7.1 照写，7.2 写不适用 |
| 8.2 业务流程 | 有多步骤或多角色流程 | 单点改动 |
| 8.3 用户路径 | 新增或改动页面跳转 | 无界面或不改跳转 |
| 8.4 页面说明 | 有界面（每个页面、弹窗附线框图和字段表，见 `wireframe.md`、`field-spec.md`） | 无界面（API、策略、数据底层） |
| 8.5 状态流转 | 对象有 3 个及以上状态 | 无状态或状态不变 |
| 8.6 角色与权限 | 多角色或有权限差异 | 单一角色且无权限变化 |
| 8.7 业务规则 | 有计算、判定、匹配、排序逻辑 | 无 |
| 8.8 接口对接 | 跨系统交互 | 单系统内 |
| 8.9 字段字典 | 有字段被 2 个及以上页面共用，或有超过 5 个值的枚举 | 字段都只在一个页面出现 |
| 九、类型扩展模块 | 类型检查项中有与本需求相关的内容 | 全部无关 |
| 十、非功能需求 | 有性能、安全、合规、兼容要求或行业包要求 | 纯文案或配置调整 |
| 十一、数据与埋点 | 有量化目标或新增数据 | 第三章写明无量化目标时 |
| 十三、上线与运营计划 | 用户可感知、需灰度、需运营或客服配合、有数据迁移 | 内部微调 |

## 五、类型与行业在各版本中的写法

| 版本 | 写法 |
| --- | --- |
| 精简版 | 不写第九章。与改动相关的类型检查项写进第八章或第十四章 |
| 核心版 | 第九章每个类型只保留相关的行；不写「9.N 行业要点」汇总，行业检查项写在对应章节 |
| 完整版 | 按 SKILL.md 第 3 步的完整规则 |

行业包中涉及法律合规、用户安全的检查项（如隐私授权、未成年人保护、危机转介、防沉迷），**任何版本都不能省略**，写在相关章节；精简版写不下时放在第十四章。

## 六、类型对章节的影响

各类型文件末尾的「通常不适用」会把对应章节或子项改为【不适用】（精简版、核心版直接省略）。多个类型冲突时，**只要有一个类型需要，就保留**。

## 七、切换版本

- 草稿阶段用户说“改成完整版”“精简一点”：保留已写内容，按新版本补齐或删减章节，版本号加 0.1（如 v0.2 → v0.3），补齐的章节按新建流程写，并补充对应的待确认问题。
- 定稿后切换版本：按 `change-management.md` 的小改处理，变更记录写“文档版本由核心版改为完整版”。
