# 检查核对已有 PRD

用户给出一份已有的 PRD，要求检查、评审、核对时使用。PRD 可以是本技能写的，也可以是其他人、其他格式写的。先出检查报告，用户确认后再出修订版。

## 第 1 步：读材料

1. 读 PRD 全文和用户一起给的原型、设计稿、截图、会议纪要；有原型或设计稿时，一起核对。
2. 判断来源：
   - 本技能写的 PRD：按四个维度检查，再加上 `quality-checklist.md` 的全部检查项。
   - 其他格式的 PRD：只按四个维度检查内容，不要求本模版的章节、编号、写法；没用本模版不算问题。
3. 按 `types/_index.md`、`industries/_index.md` 判断类型和行业，读对应文件，把其中的检查项一起核对；行业法规类检查项必须检查。
4. 用户指定了检查重点时，例如“只看能不能开发”“只看测试能不能写用例”，只检查相关维度，报告开头写明范围。

## 第 2 步：按四个维度检查

| 维度 | 检查什么 |
| --- | --- |
| 完整性 | 背景和目标、本期做与不做、功能清单、流程与分支、页面与操作、字段（必填、长度格式、选项、默认值、校验与提示）、空状态和异常、权限、状态流转、对接系统、验收标准；类型和行业检查项 |
| 确定性 | TBD、待定、待确认、推测；“等”“适当”“合理”“友好”“快速”“尽量”这类模糊词；没有数值的时长、数量、范围；未定的提示文案 |
| 一致性 | 同一功能、字段、状态、术语在不同位置说法不同；流程图、原型、文字互相矛盾；指标没有口径；功能没有规则或验收 |
| 可测试性 | 每个功能有能观察到的预期结果；异常和边界有预期；字段边界能算出测试值；验收标准能判断通过与否 |

- 每个问题写清原文位置：章节标题，或引用原文片段，便于对方定位。
- 只指出问题、给建议改法；建议里的具体值标“建议”，不当作已确认的内容。
- 不报表达偏好：用词、排版、章节顺序只要不影响理解和开发，不列为问题。
- 同一个问题在多处出现时合并为一条，位置写全。

## 第 3 步：输出检查报告

```
## PRD 检查报告：会员积分兑换 PRD v1.2

结论：修改后进入开发
依据：致命 0 / 严重 3 / 一般 5 / 建议 2；影响测试的问题 6 个

| 编号 | 维度 | 位置 | 问题 | 严重程度 | 影响测试 | 建议改法 |
| --- | --- | --- | --- | --- | --- | --- |
| C-01 | 确定性 | 4.2 兑换规则 | “积分不足时给出提示”没有提示文案 | 一般 | 是 | 写明文案，建议“积分不足，还差 N 分” |
| C-02 | 一致性 | 3.1 功能列表、5.3 兑换记录页 | 3.1 写“兑换后不可取消”，5.3 有“取消兑换”按钮 | 严重 | 是 | 确认是否支持取消，删掉另一处 |
```

| 严重程度 | 判断 |
| --- | --- |
| 致命 | 主流程、资金、隐私、合规的规则缺失或互相矛盾，开发无法进行 |
| 严重 | 缺规则、预期不明、前后矛盾，影响功能实现或测试判断 |
| 一般 | 局部缺失：字段格式、提示文案、空状态、异常提示 |
| 建议 | 不影响开发的结构和表达优化 |

| 结论 | 条件 |
| --- | --- |
| 不能进入开发 | 有致命问题 |
| 修改后进入开发 | 没有致命问题，有严重问题 |
| 可以进入开发 | 只有一般问题和建议 |

- 问题按严重程度排序，同级按文档顺序。超过 30 个时先列致命和严重问题，再问用户是否列出其余问题。
- “影响测试”列标出会导致测试用例无法写出或无法判断的问题，生成测试用例时先处理这些问题。
- 报告最后一行写：“需要我按检查结果出修订版吗？也可以只改指定的问题，例如‘改 C-01 到 C-05’。”
- 不主动出修订版。

## 第 4 步：出修订版（用户确认后）

1. 只改用户指定的问题；用户说“都改”时改报告中的全部问题。不加报告以外的新功能。
2. 修改需要用户决定的内容时，例如规则、数值、文案，先按新建流程第 2 步的方式提问：一轮最多 8 个，每个附建议答案；确认不了的放进“本期不做”。
3. 本技能写的 PRD：按 `change-management.md` 更新版本号和需求变更记录，变更内容写“按检查报告修订：C-01、C-02……”。
4. 其他格式的 PRD：先问用户保持原格式，还是改写成本模版。
   - 保持原格式：只改有问题的地方，其他内容和结构不动；输出完整修订版，并列出改了哪些位置。
   - 改写成本模版：按新建流程第 1 步选版本、板块和交付方式，默认推荐覆盖原 PRD 已有内容的最小版本；改写后遵守写作铁律。原 PRD 有版本号时接着递增，没有时为 v1.0；需求变更记录第一行写“按检查报告修订，原文档：【原名称和版本】”。
5. 修订后按 `quality-checklist.md` 自检；保持原格式时只检查四个维度。
